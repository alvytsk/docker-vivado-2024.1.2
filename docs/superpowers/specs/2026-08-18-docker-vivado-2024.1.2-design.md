# Design: Headless Vivado 2024.1.2 Docker image for Zynq-7000 CI/CD

Date: 2026-08-18
Status: Approved 2026-08-18 (after three review rounds)

## 1. Goal

Produce a reproducible, headless Docker image containing AMD Vivado ML Standard
2024.1 updated to 2024.1.2, restricted to the **license-free Zynq-7000 subset**,
whose purpose is to run synthesis and implementation in CI and emit `.xsa` and
`.bit` artifacts.

That subset is XC7Z007S, XC7Z010, XC7Z012S, XC7Z014S, XC7Z015, XC7Z020 and
XC7Z030. It is narrower than the Zynq-7000 family: see non-goals.

All AMD content comes from the local offline media in `D:\Projects\Xilinx_2024.1`
(`/mnt/d/Projects/Xilinx_2024.1` under WSL). The build needs no Xilinx account, no
network installer, and no license file, and contacts no AMD host. It is not
network-free in the absolute sense — see section 8a.

## 2. Non-goals

- No GUI. No X11 stack, no VNC, no desktop. Invocation is `vivado -mode batch`.
- No Vitis in the default image. See section 10 for the additive path.
- No PetaLinux, no Vivado Lab, no Vitis Model Composer, no DocNav.
- No license file baked into the image, and specifically no use of the
  `Crack/Xlnx_2024.lic` keygen license or `IP_Decryptor_13.7z` found alongside
  the media. Vivado ML Standard needs no license for the target devices, so this
  costs the project nothing.
- No device families beyond Zynq-7000.
- **No XC7Z035, XC7Z045 or XC7Z100.** These are Zynq-7000 parts, but they fall
  outside Vivado ML Standard and require an Enterprise license. The installer's
  `Zynq-7000` module installs their device data regardless, so the image will
  appear to support them and will then fail at synthesis with a licensing error.
  Supporting them is a licensing decision, not a packaging one, and is out of
  scope. Section 13 makes the failure mode explicit and tested rather than
  latent.

## 4. Licensing decision

Vivado ML Standard Edition requires no license file. Its Zynq-7000 device support
covers XC7Z007S, XC7Z010, XC7Z012S, XC7Z014S, XC7Z015, XC7Z020 and XC7Z030.

This is a subset of the Zynq-7000 family, not the whole of it. XC7Z035, XC7Z045
and XC7Z100 are Zynq-7000 devices that Standard does not cover. Because device
data ships with the family module while the restriction is enforced by licensing
at tool runtime, a user can open a 7Z045 project in this image and only discover
the limit when synthesis fails. The project accepts that boundary and documents
it; it does not attempt to work around it.

Therefore the image ships with no license and sets no `XILINXD_LICENSE_FILE`. If a
future design targets a part outside Standard's support list, the runtime contract
in section 9 already allows a license to be supplied by environment variable or by
bind-mounting a file to `~/.Xilinx` — no image change required.

## 5. Architecture

A pure `docker build` is rejected: BuildKit would have to walk and snapshot a
116 GB context across the WSL drvfs boundary. Extracting the ISO to disk first is
also rejected: it costs 116 GB of scratch space and then either bloats layers or
requires an HTTP-server workaround.

The build is instead three stages, driven by a `Makefile`:

**Stage 1 — base image (`docker build`).** `docker/Dockerfile.base` builds
`vivado-base:22.04` from `ubuntu:22.04` with the OS packages Vivado needs. Small,
fast, cacheable, fully idiomatic.

**Stage 2 — install (`docker run` + `docker commit`).** `scripts/install.sh` runs a
`--privileged` container from `vivado-base:22.04` with the media directory
bind-mounted read-only at `/media`. Inside, it loop-mounts the base ISO, runs
`xsetup` in batch mode against the config from section 7, unmounts, loop-mounts the
update ISO, runs `xsetup -b Update`, and exits. The host then commits the container
to `vivado-tools:2024.1.2-raw`.

This is the only unusual step, and it is what makes the build tractable: the ISO is
never copied, never enters a build context, and never lands in a layer. Only the
installed tree consumes space.

**Stage 3 — final image (`docker build`).** `docker/Dockerfile.final` starts
`FROM vivado-tools:2024.1.2-raw` and adds the runtime contract only: non-root
user, entrypoint, environment, workdir, labels. Tagged `vivado:2024.1.2`.

**Cleanup happens in stage 2, never in stage 3.** Docker layers are additive, so
deleting installer scratch in `Dockerfile.final` would write whiteouts while the
bytes stayed in the parent layer and continued to be pushed and pulled. All
pruning of anything *stage 2 creates* — installer scratch, `/tmp/xinstall`,
unpacked payload — therefore runs inside `container-install.sh` immediately
before the container exits, in this order:

1. `xsetup` install, then `xsetup -b Update`.
2. Copy installer logs to `/var/log/xinstall/` (small, retained deliberately so a
   later support question is answerable from the image itself).
3. Delete scratch and caches — **preserving `/tools/Xilinx/.xinstall`**. That
   directory is the installer's own record of what was installed; `xsetup -b Add`
   and `-b Update` both read it. Deleting it as "installer scratch" would leave a
   working Vivado image in which the section 10 Vitis path and any future update
   silently cannot run. It looks exactly like scratch and is not.
4. Exit; the host then commits.

The same rule applied one layer earlier: apt lists are created in **stage 1**, so
removing them from the stage-2 container would hide bytes already committed to
the base layer. `rm -rf /var/lib/apt/lists/*` therefore runs in the same stage-1
`RUN` instruction that installs the packages, never later. The general form of
the rule is: scratch is deleted in the same stage that created it, or not
usefully at all.

This is the same layer-additivity constraint described in section 10 for Vitis,
applied to scratch instead of tools. Any future cleanup idea must be checked
against it: if it is not in stage 2, it does not shrink anything.

Rebuilding stage 3 is seconds. Stage 2 re-runs only when the build key in
section 5a changes.

### Data flow

```
/mnt/d/.../Unified.iso ─┐
                        ├─(ro bind)→ privileged container ─(xsetup)→ /tools/Xilinx ─(commit)→ :raw ─(build)→ :2024.1.2
/mnt/d/.../Update.iso  ─┘
```

## 5a. Stage-2 reuse and the build key

Stage 2 runs outside `docker build`, so Docker's own cache cannot see changes to
the ISOs, the config, the install scripts, or the base image. A fixed `:raw` tag
would silently reuse a stale install. Reuse is therefore gated on an explicit
build key.

The key is the SHA-256 of a manifest containing:

- the base image ID of `vivado-base:22.04` (`docker image inspect -f '{{.Id}}'`),
- the SHA-256 of `config/install_config.vivado.txt`,
- the SHA-256 of **every host-side input that affects stage 2**, not just the
  in-container script: `scripts/container-install.sh`, `scripts/install.sh`, and
  `docker/Dockerfile.base`,
- the values of the Makefile variables that reach stage 2 (media path, install
  destination, image tags, container name), serialised into the manifest,
- a media identity record for each ISO (below).

`install.sh` owns the container invocation, its mounts, its environment and the
commit itself, so hashing only `container-install.sh` would let host-side
orchestration change while the key stayed put and a stale `:raw` image was
reused. The manifest is therefore built from every effective input; the rule for
future edits is that anything which can change what stage 2 produces belongs in
the manifest.

`install.sh` computes the key, compares it against the
`org.opencontainers.image.revision` and `build.key` labels on any existing
`vivado-tools:2024.1.2-raw`, and reuses the image only on an exact match.
Otherwise it rebuilds and stamps the new key as a label.

**Media identity is the one place this deviates from a pure content hash, and it
is a deliberate trade-off.** Hashing 164 GB of ISO across the WSL drvfs boundary
costs roughly ten to twenty minutes, imposed on every build — including the ones
where the key check exists precisely to avoid doing work. So the default media
record is `(absolute path, size in bytes, mtime)` per ISO. These are write-once
release ISOs; that tuple changes if the file is replaced and does not change
spuriously.

Full content hashing remains available and is not merely theoretical:

- `make verify-media` computes real SHA-256 for both ISOs and records them in
  `config/media.sha256`.
- If that file exists, `install.sh` uses the recorded hashes in the key instead of
  the size/mtime tuple, and fails if a re-computed hash disagrees.

The label records which mode produced the key, so an image built under the cheap
mode is never mistaken for one built under the verified mode. If media integrity
turns out to matter more than build latency, deleting the branch and always
hashing is a one-line change.

This build key also supersedes the weaker "non-truncated by size" media check
that section 12 previously relied on.

## 6. Repository layout

```
docker-vivado-24.1.2/
├── Makefile                       # build / install / test / clean targets
├── README.md
├── docker/
│   ├── Dockerfile.base            # stage 1
│   └── Dockerfile.final           # stage 3
├── config/
│   ├── install_config.vivado.txt  # default variant: Vivado only, Zynq-7000
│   └── add_config.vitis.txt       # optional variant: adds Vitis Embedded Dev
├── scripts/
│   ├── install.sh                 # stage 2 orchestration (runs on host)
│   ├── container-install.sh       # runs inside the privileged container
│   └── entrypoint.sh              # runtime entrypoint
├── test/
│   ├── zynq_smoke.tcl             # minimal Zynq-7020 design → .xsa + .bit
│   └── run-smoke.sh
└── docs/superpowers/specs/
```

Each unit has one job: `container-install.sh` knows about ISOs and `xsetup` and
nothing about Docker; `install.sh` knows about Docker and nothing about `xsetup`;
`entrypoint.sh` knows only about the runtime environment.

## 7. Install configuration

Generated with `xsetup -b ConfigGen -p Vivado -e "Vivado ML Standard"` against the
actual media, then reduced. The module names below are verbatim from the installer
and must not be paraphrased — `xsetup` matches them literally.

`config/install_config.vivado.txt`:

```
Edition=Vivado ML Standard
Product=Vivado
Destination=/tools/Xilinx
Modules=Virtex UltraScale+ HBM:0,Kintex UltraScale:0,Vitis Networking P4:0,Artix UltraScale+:0,Spartan-7:0,Artix-7:0,Virtex UltraScale+:0,Vitis Model Composer(Toolbox for MATLAB and Simulink. Includes the functionality of System Generator for DSP):0,DocNav:0,Zynq UltraScale+ MPSoC:0,Zynq-7000:1,Virtex UltraScale+ 58G:0,Power Design Manager (PDM):0,Vitis Embedded Development:0,Kintex-7:0,Install Devices for Kria SOMs and Starter Kits:0,Kintex UltraScale+:0
InstallOptions=
CreateProgramGroupShortcuts=0
ProgramGroupFolder=Xilinx Design Tools
CreateShortcutsForAllUsers=0
CreateDesktopShortcuts=0
CreateFileAssociation=0
EnableDiskUsageOptimization=1
```

Every device family except `Zynq-7000` is deselected. `DocNav` and
`Vitis Model Composer` are deselected because they are useless headless. All
shortcut and file-association options are off. `EnableDiskUsageOptimization=1` is
retained deliberately — it is the installer's own post-install size reduction.

Install location is `/tools/Xilinx`, the installer's default and the AMD
convention, giving `/tools/Xilinx/Vivado/2024.1/settings64.sh`.

## 8. Base image and prerequisites

Ubuntu 22.04 LTS. AMD qualifies it for 2024.1; 20.04 (as used by the
`gusanagy/xilinx-vivado` reference image) is a release behind.

**The base image is pinned by digest, not by tag.** Tags are mutable, so
`FROM ubuntu:22.04` alone would let a clean rebuild silently pick up a different
base even with an unchanged build key. `Dockerfile.base` uses:

```
FROM ubuntu:22.04@sha256:2edbbc5dc405e9612ba3584ce95480277e3eb374407b5505fe26f17df77c7dbc
```

That digest is the manifest recorded when the image was pulled on this host on
2026-08-18. Updating it is a deliberate edit, and because the resolved base image
ID feeds the section 5a build key, changing it forces a stage-2 rebuild.

Packages, kept to what a headless batch flow actually needs: `libtinfo5`,
`libncurses5`, `libx11-6`, `libxext6`, `libxrender1`, `libxtst6`, `libxi6`,
`libfreetype6`, `libfontconfig1`, `locales`, `ca-certificates`, `gosu`, `unzip`,
`zip`, `tar`, `git`, `make`, `python3`, `net-tools`, `procps`.

`gosu` is load-bearing, not incidental: the section 9 entrypoint drops privileges
with it on every root-mode invocation, so omitting it breaks the default run path
with `gosu: command not found`. Acceptance criterion 8 tests the privilege drop
directly rather than assuming it.

The X libraries are not for a GUI — several Vivado binaries link them
unconditionally even in batch mode, and omitting them produces load failures at
`vivado -mode batch` startup. This is the single most common cause of a
"headless" Vivado image failing on first run, and is why they stay.

Locale is set to `C.UTF-8`; Vivado emits encoding warnings otherwise.

### What "reproducible" claims

Pinning the digest fixes the base image but not the Ubuntu package versions,
which float as the mirrors advance. Rather than stand up a snapshot apt
repository — disproportionate for this project — the claim is scoped explicitly:

**Reproducible here means input-tracked and functionally stable, not
bit-identical.** Every input that determines *what AMD software is installed and
how* is pinned or hashed: both ISOs, the install config, the install scripts, and
the base image digest. Ubuntu package versions are the one unpinned input; they
affect the surrounding OS, not Vivado's behaviour. Two builds a month apart will
produce images with the same Vivado install and possibly different `libfreetype6`
patch levels.

If bit-identical rebuilds are ever needed, the missing pieces are a pinned apt
snapshot and a fixed `SOURCE_DATE_EPOCH`; the design does not preclude them.

The ISO ships `installLibs.sh`, which installs distro prerequisites. It is
deliberately not used: it is interactive-leaning, pulls a broader set than a
headless image needs, and would run at install time rather than in a cacheable
base layer.

## 8a. What "offline" means here

The goal deliberately says *no AMD network access*, not *no network access*.
Stage 1 pulls `ubuntu:22.04` from a registry and installs packages from Ubuntu
mirrors; neither is on the AMD media, and no combination of the two ISOs can
supply them. Claiming a fully air-gapped build would be false.

The guarantee actually made, and tested:

- No connection to any `xilinx.com` or `amd.com` host at any point.
- No Xilinx account, no `AuthTokenGen`, no web installer.
- Every byte of AMD software originates from the two local ISOs.
- Stage 2 and stage 3 run with networking disabled outright (`--network=none`),
  which mechanically enforces the above for the install itself.

Stage 1 is the only step needing a network, and only for Ubuntu content. Making
even that offline would mean vendoring a base-image tarball and a local apt
repository. That is a coherent option and is left open — `install.sh` accepts a
pre-pulled base image and skips the pull — but it is not built by default,
because the benefit is limited for a build already pinned to a specific base
image digest.

## 9. Runtime contract

- **User.** Non-root `vivado` user, created at build time with UID/GID 1000.
  That default alone does **not** give correct file ownership on a runner whose
  account is not 1000, so ownership is reconciled at *runtime*, not baked in:

  - `/work` is created in the image owned by `1000:1000`, so the unmounted case
    already presents a sane, non-root owner.
  - The entrypoint starts as root, reads `HOST_UID` / `HOST_GID`, falling back to
    the numeric owner of `/work` when they are unset. **A UID or GID of 0 is never
    adopted.** An explicit `HOST_UID=0` is refused outright and falls straight
    through to the default `vivado` IDs rather than to the `/work` owner —
    quietly resolving a deliberate root request to some other identity would be
    more surprising than denying it. A `/work` owner of 0 is likewise ignored
    and the default IDs are kept. Without that guard, running the image with no bind
    mount — or with a root-owned one — would try to remap `vivado` to UID 0,
    which either collides with root or silently breaks the non-root contract.
    Criteria 2 and 6 invoke the image with no `/work` mount, so this is the
    ordinary path, not an edge case.
  - It then drops privileges with **numeric** `gosu "$uid:$gid"`. It does **not**
    `usermod`/`groupmod` the `vivado` account. Those commands reject a target ID
    already assigned to another account — UID/GID 65534 collides with
    `nobody`/`nogroup` on any Ubuntu base — so reconciling by mutation would fail
    on exactly the arbitrary IDs the mechanism exists to support. `gosu` accepts
    numeric IDs that need not resolve to an account at all, which removes the
    collision class outright.
  - So that tools which expect a resolvable account still work, the entrypoint
    appends a `/etc/passwd` and `/etc/group` entry for the target ID **only when
    that ID is absent**. When it is already present (the `nobody` case), the
    existing entry is reused untouched. The container is ephemeral, so writing to
    these files at startup is safe.
  - If the container is started with an explicit `--user`, the entrypoint is
    already non-root and cannot edit `/etc/passwd`; it detects this and skips
    both reconciliation and the passwd write. This is the mode CI should prefer.

### HOME is set explicitly, in every branch

`gosu` performs `setuid`/`setgid`/`setgroups` and then `exec`s — it does not
construct a login environment. A process started as root and dropped to `vivado`
would therefore **inherit `HOME=/root`**, which the non-root process cannot
write. That silently breaks Vivado's user-data directory and the `~/.Xilinx`
licensing hook that section 4 relies on as the escape route for future licensed
parts.

The entrypoint therefore exports `HOME` itself, in both the root-entry and
`--user` branches, and never relies on inheritance:

- `/home/vivado` is created at build time mode `0777`, so it is writable
  whatever ID the container ends up running as. This image is a single-purpose
  build tool, not a multi-tenant host, so the permissive mode costs nothing real.
- The entrypoint sets `HOME=/home/vivado`, then verifies `test -w "$HOME"` and
  falls back to a freshly created directory under `/tmp` if that ever fails —
  a writable `HOME` is a hard requirement, not a best effort.

Criterion 8 asserts `id -u`, `$HOME` and `test -w "$HOME"` together, because
checking the UID alone would pass while `HOME` still pointed at `/root`.

One image therefore serves any runner UID without a rebuild, with the documented
limit that IDs already present in the image reuse that existing account's name.
Vivado writes freely into its project directory and misbehaves as root in some
flows, so dropping privileges is not optional.
- **Entrypoint.** `scripts/entrypoint.sh` sources
  `/tools/Xilinx/Vivado/2024.1/settings64.sh` and then, **if it exists**,
  `/tools/Xilinx/Vitis/2024.1/settings64.sh`, before `exec "$@"`. This keeps
  `docker run vivado:2024.1.2 vivado -mode batch -source build.tcl` working without
  the caller knowing about `settings64.sh`. Default `CMD` is `bash`.
  The Vitis line is conditional rather than absent so that one entrypoint serves
  both images: the default image has no Vitis and skips it, while the section 10
  variant gets the environment AMD's 2024.1 setup instructions require. Shipping
  the Vitis settings script without sourcing it does not put `xsct` on `PATH`.
- **Workdir.** `/work`, intended as the bind-mount point for the design repo.
- **Environment.** `XILINX_LOCAL_USER_DATA=no` to stop Vivado writing into
  `~/.Xilinx` on every invocation, which otherwise dirties containers and can fail
  on read-only home directories.
- **Licensing hook.** No license shipped. `XILINXD_LICENSE_FILE` is left unset and
  is honoured if the caller sets it.

## 10. Vitis variant

Vitis is excluded by default. It roughly doubles image size and is not needed to
produce `.xsa` or `.bit` — only to build FSBL, BOOT.BIN, or application ELFs.

The choice is deliberately not load-bearing, because the installer exposes an `Add`
batch action. Adding Vitis later is a new layer on top of the existing image, not a
rebuild:

```
make add-vitis   # runs xsetup -b Add -c config/add_config.vitis.txt
                 # against the same mounted media, tags vivado-vitis:2024.1.2
```

`config/add_config.vitis.txt` is the same file with
`Vitis Embedded Development:1` and `Product=Vitis`.

The reverse is not symmetric and the README must say so: because Docker layers are
additive, uninstalling Vitis later would delete the paths without reclaiming the
bytes. Shrinking requires re-running stage 2. This asymmetry is the reason the
default is the smaller image.

## 11. Size and distribution

Expected: roughly 20-40 GB for a Zynq-7000-only Vivado ML Standard install, against
867 GB free. This is an estimate from comparable single-family installs, not a
measurement; section 14 tracks confirming it.
Stage 2 peak usage is higher, since the installer stages payload before pruning.

For CI this is still large. The README will recommend a self-hosted or local
registry rather than Docker Hub, and the two-image split already supports it: the
fat `vivado-tools` layer changes only when the media changes, so runners pull it
once and subsequently pull only the thin stage-3 layer.

## 12. Failure modes and handling

| Failure | Handling |
| --- | --- |
| Media directory missing or ISO absent | `install.sh` fails fast naming the expected path while computing the section 5a build key, which reads both ISOs' identity as a side effect |
| Media replaced between builds, changing size or mtime | Build-key mismatch forces a stage-2 rebuild rather than reusing a stale `:raw` image |
| Media replaced or corrupted while preserving path, size and mtime | **Not detected in default mode** — the cheap identity record is metadata-only. Content-integrity detection requires `make verify-media`, which records true SHA-256 hashes and fails on disagreement. Section 5a states this trade-off; the guarantee is deliberately conditional |
| Loop mount fails (no `--privileged`, no loop device) | `container-install.sh` checks the mount succeeded and aborts with a clear message rather than running `xsetup` against an empty directory |
| `xsetup` non-zero exit | `container-install.sh` runs under `set -euo pipefail`; the installer log is copied to `/tmp/xinstall` and `install.sh` extracts it from the stopped container before removal, so a failed build is diagnosable |
| Update applied before base install | `container-install.sh` asserts `/tools/Xilinx/Vivado/2024.1/settings64.sh` exists before running `-b Update` |
| Interrupted stage 2 | The container is named deterministically; `install.sh` removes any stale container of that name before starting |
| Disk exhaustion mid-install | Pre-flight check for a configurable minimum free space on the Docker volume |

## 13. Acceptance criteria

The build is done when all of the following hold:

1. `make build` completes from a clean Docker state with no Xilinx account, and
   with stages 2 and 3 run under `--network=none`, proving no AMD host is
   contacted. Stage 1's Ubuntu network use is expected — see section 8a.
2. `docker run --rm vivado:2024.1.2 vivado -version` reports version 2024.1.2, not
   the un-updated 2024.1.
3. `make test` runs `test/zynq_smoke.tcl` — a minimal XC7Z020 block design with a
   Zynq PS — end to end and produces both a non-empty `.bit` and a non-empty
   `.xsa` in a bind-mounted `/work`.
4. The smoke test emits no license error and the image contains no `.lic` file.
5. Files written to the bind-mounted `/work` are owned by the invoking host UID,
   verified with a **non-1000 UID** (the test runs the smoke flow as UID 1234 via
   both `HOST_UID=1234` and `--user 1234:1234`, and asserts ownership both ways).
   A **third case** supplies neither override and bind-mounts a directory owned
   by a non-1000 UID, exercising the `/work`-owner inference path specifically —
   without it, an entrypoint that never inspects `/work` would pass every other
   criterion. Testing only at 1000 would pass vacuously.
6. `docker run --rm vivado:2024.1.2 bash -c 'echo $XILINX_VIVADO'` resolves without
   the caller sourcing anything.
7. Building for an out-of-subset part (XC7Z045) fails with a recognisable AMD
   licensing error rather than a confusing tool crash, and the README names the
   three unsupported parts. This turns the section 2 boundary into something
   observable instead of latent.
8. In the no-bind-mount case that criteria 2 and 6 exercise, a single invocation
   asserts all three of: `id -u` is non-zero (the `gosu` drop ran), `$HOME` is
   not `/root` (it was set rather than inherited), and `test -w "$HOME"`
   succeeds. Checking the UID alone would pass while `HOME` still pointed at an
   unwritable `/root`.
9. `make add-vitis` succeeds against the committed image and the result answers
   `xsct -eval "puts [version]"` headlessly, reporting 2024.1.2, with
   `XILINX_VITIS` set in the container environment. Without this,
   the section 10 promise could be broken — by the unresolved `Add` config form,
   by cleanup having removed `.xinstall`, or by the update not applying to the
   added tools — while every other criterion still passed. The variant is
   built and tested once, via a separate `make` target, so it does not gate
   routine default builds.

Criterion 3 is the real test: it exercises synthesis, implementation, bitstream
generation and hardware handoff, which is exactly the CI workload.

## 14. Items to resolve during implementation

- Exact batch syntax for the update ISO. `-b Update` is confirmed to exist; whether
  it takes `-c <config>` or `-l /tools/Xilinx` must be read from the update ISO's
  own `xsetup --help` as the first implementation step.
- Whether `-b Add` for Vitis requires the config to name only the delta or the full
  module list. Resolve by running `ConfigGen` on the update media.
- Whether `EnableDiskUsageOptimization=1` measurably reduces the Zynq-7000-only
  install; if not, drop it to save install time.
- Whether the `Zynq-7000` module alone carries all device data needed for XC7Z020
  synthesis, or whether `Artix-7` and `Kintex-7` must also be selected because the
